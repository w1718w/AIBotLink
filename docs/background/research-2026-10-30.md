# IM Agent Gateway 开源实现调研

调研日期：2026-10-30（北京时间）。对象：[任务书](task-book.md)。本报告是选型研究，不代表已实施的架构；初轮调研阶段未修改任务书、安装服务或运行真实 Agent 任务。

后续已补充[本机协议验证与选型判断](validation-2026-10-30.md)，并据此修订任务书。下文保留初轮研究的证据范围；涉及本机验证状态时以后续验证报告为准。

## 结论与建议

原任务书的核心约束仍然适用：独立网关、管理命令不用 LLM、保留原生 Agent、两台 Windows 独立部署、权限与会话不串线。需要更新的是候选实现、协议细节和选型顺序。

建议取消“默认优先 Zhin”和“DSH 必须先开发 Companion”两个预设，改为比较三条路线：

1. **现成桥接器适配**：先评估 cc-connect 能否满足独立启动、QQ 原生交互、Codex App Server 和 DSH ACP。已有代码覆盖面最接近需求，但存在明确冲突，不能直接宣布采用。
2. **轻量 TypeScript 网关**：直接 QQ SDK 或 Zhin 的 IM 核心，加 Codex App Server；DSH 优先验证现有 ACP，只有桌面 Host 控制所必需的差异才用 Companion 补齐。这是当前更可控的自建方向。
3. **Python IM 底座**：Octop Gateway 可作多 IM 传输层，但不会替项目解决 Agent 会话、审批、命令注册和进程所有权；采用前应核算其平台依赖规模。

新增重点参考：**cc-connect、HAPI、agent-wechat-bridge**。保留 dsh-im 作为 DSH Host 与 QQ 体验的主要参考。Takopi 可参考会话路由和任务控制，但它的自动审批行为不符合原任务书要求。

目前未找到一个已经证明同时满足“Windows + QQ 原生面板 + Codex + DSH 桌面原生会话 + Agent 故障隔离”的现成完整替代品。这里的“未找到”只覆盖本次检索与核查范围。

## 研究方法与证据强度

- 通过搜索发现项目，再读取 GitHub 仓库树、必要源码、包元数据和许可证；关键结论使用固定提交链接。
- 检查了 12 个主要仓库的元数据与目录，其中重点阅读 9 个桥接器/底座的相关代码，另核对 QQ SDK 和 Codex 官方协议文档。
- 下文“源码存在”表示已找到实现，不表示已在本机或真实账号下通过验证。
- 本次没有 QQ/iLink 实机收发、Windows 进程管理、付费模型调用或桌面会话接管测试；不把上游自述的测试结果当成本项目验收结果。
- 表中的最近推送日来自 GitHub `pushed_at`，统一按 UTC 日期列出；它可能包含其他分支活动，不等同于最近正式发版或维护质量。

## 新增重点实现的源码发现

### cc-connect：最接近现成产品，但有三处实质冲突

已验证的代码：

- `platform/qqbot/qqbot.go` 是 QQ 官方机器人实现，与 `platform/qq` 的另一接入路线分开。含 `INTERACTION_CREATE`、按钮发送和回调 ACK；本次读到的回调分发主要面向 `perm:` 审批数据，不能据此声称它已具备任意管理命令按钮或 QQ 原生指令面板同步。[QQ 源码](https://github.com/chenhg5/cc-connect/blob/7f671b15ed02250d4e356b46a760a7a5ce86c427/platform/qqbot/qqbot.go)
- Codex 有 `exec` 和 `app_server` 两种后端；未指定时落到 `exec`。App Server 路径有线程启动/恢复、Turn、命令/文件/权限审批和用户提问处理。[后端选择](https://github.com/chenhg5/cc-connect/blob/7f671b15ed02250d4e356b46a760a7a5ce86c427/agent/codex/codex.go)、[App Server 实现](https://github.com/chenhg5/cc-connect/blob/7f671b15ed02250d4e356b46a760a7a5ce86c427/agent/codex/appserver_session.go)
- 通用 ACP Adapter 支持配置 command/args，探测会话列表能力，并从握手获取权限模式。它提供了接入 DSH ACP 的可能性，尚未证明与当前 DSH 兼容。[ACP 实现](https://github.com/chenhg5/cc-connect/blob/7f671b15ed02250d4e356b46a760a7a5ce86c427/agent/acp/agent.go)

与任务书冲突：

1. **会话文件写入**：`listCodexSessions()` 会调用 `patchSessionSource()`，后者将 exec 会话 JSONL 首行的 `source`、`originator` 改成 CLI 值。连“列会话”路径都可能写原生记录，直接违背“不篡改私有会话文件”。复用时应改为原生 `thread/list`、分页历史等接口。[实现及调用位置](https://github.com/chenhg5/cc-connect/blob/7f671b15ed02250d4e356b46a760a7a5ce86c427/agent/codex/list.go)
2. **Agent 缺失时的网关启动**：Codex `New()` 会查找可执行文件，不存在就返回错误；README 也提示应先装好配置的 Agent 才能启动。是否影响整台网关必须实测，不能默认符合“某 Agent 未安装时其他链路仍可用”。[初始化代码](https://github.com/chenhg5/cc-connect/blob/7f671b15ed02250d4e356b46a760a7a5ce86c427/agent/codex/codex.go)、[README](https://github.com/chenhg5/cc-connect/blob/7f671b15ed02250d4e356b46a760a7a5ce86c427/README.md)
3. **许可材料**：README 声明 MIT，但本次完整仓库树未发现 LICENSE/NOTICE 文件，GitHub 也未识别许可证。应补核授权文本后再复制代码；这不等于断言项目禁止复用。

判断：应加入第一轮现成方案对比，但不宜仅凭功能列表决定 Fork。上述冲突如果需要侵入核心持续维护，自建薄网关可能反而更省事。

### HAPI：共享会话与 DSH ACP 的重要参考

其 DSH Backend 已使用通用 ACP，实现默认命令 `dsh --profile acp`，支持受控参数与环境配置。这表明新版提示词应先验证 ACP 路线，而不是要求起手就写 Host 插件。[DSH Backend](https://github.com/tiann/hapi/blob/f8e55fb930cde45dd4ef5cc5dd1fac0a047f38b8/cli/src/dsh/utils/dshBackend.ts)

Codex 客户端具有线程、Turn、Steer、Compact 等明确协议调用。[客户端源码](https://github.com/tiann/hapi/blob/f8e55fb930cde45dd4ef5cc5dd1fac0a047f38b8/cli/src/codex/codexAppServerClient.ts)

共享会话文档特别值得借鉴：将终端、远端连接到同一 app-server；区分执行所有者和附加终端；拒绝冷恢复另一个存活执行所持有的线程；审批以原生 resolved 事件结束；结果未知的写入不盲目重放。文档要求 Codex 0.154.0+，并明确 Windows 原生执行仍需平台验证。这是上游声明的范围，不是本机验证结论。[共享会话契约](https://github.com/tiann/hapi/blob/f8e55fb930cde45dd4ef5cc5dd1fac0a047f38b8/docs/guide/codex-shared-sessions.md)

根目录与 `cli/LICENSE` 都是 AGPL-3.0，不能当成 MIT 片段直接并入另一许可证项目；本报告不判断具体分发义务。可先作为设计与协议使用参考。[许可证](https://github.com/tiann/hapi/blob/f8e55fb930cde45dd4ef5cc5dd1fac0a047f38b8/LICENSE)

### agent-wechat-bridge：近期轻量实现，也是桌面接管风险的实证

本次包元数据为 0.4.1，MIT；包没有声明运行时 dependencies。它把微信、OpenCode 插件、Codex Hooks 与独立 daemon 组合，值得参考小规模部署方式。[包元数据](https://github.com/xixi25937/agent-wechat-bridge/blob/345303baf55b66a486dae2a6c93f99ded5eb7bef/package.json)

但 Codex 控制有两条完全不同的路径：

- 自己启动的 `codex app-server`：stdio JSON-RPC、thread/turn、停止、历史等。
- 已由 Desktop 加载的会话：通过桌面 IPC 调用 `thread-follower-start-turn` 等方法；源码注明消息版本表来自 Desktop `app.asar`，绑定桌面 26.1023。

因此，“支持桌面会话”不能被表述成“官方 App Server 可任意接管桌面”。这个项目证明了能做桥接，也明确暴露了私有协议维护成本。[两条控制路径](https://github.com/xixi25937/agent-wechat-bridge/blob/345303baf55b66a486dae2a6c93f99ded5eb7bef/codex.js)

建议只借鉴 daemon、按后端所有权路由、进度与发送配额、附件交付等思路。桌面私有 IPC 应作为明确可选实验，不能偷偷变成主路径；本次未全面审计该项目身份与文件发送边界。

## 原有候选需要如何重新定位

### Zhin：仍有价值，版本与职责描述要更新

当前核查到 `@zhin.js/core` 为 1.1.53、QQ Adapter 为 1.1.18，QQ SDK 依赖 `^1.3.3`。原文“4.x API 稳定性”已不适合作为当前检查项；这些是仓库包版本，不代表本次核验了 npm 发布产物。[Core 包](https://github.com/zhinjs/zhin/blob/78e5830a718f12980122710b82c4e401fba99439/packages/im/core/package.json)、[QQ 包](https://github.com/zhinjs/zhin/blob/78e5830a718f12980122710b82c4e401fba99439/plugins/adapters/qq/package.json)

Core 的运行依赖不包含 AI 包，AI 位于 devDependencies，支持只用 IM 核心的方向。QQ Adapter 已有 action 归一化，文档展示通过底层 SDK 操作菜单和面板；本次没有找到足够证据证明业务命令可自动同步到 QQ 指令面板。[交互实现](https://github.com/zhinjs/zhin/blob/78e5830a718f12980122710b82c4e401fba99439/plugins/adapters/qq/src/interaction.ts)、[QQ 接入说明](https://github.com/zhinjs/zhin/blob/78e5830a718f12980122710b82c4e401fba99439/docs/adapters/qq.md)

### Octop：传输职责清楚，但不等于依赖最少

`pyproject.toml` 当前为 1.0.3、Python >=3.12；必选依赖包括飞书、钉钉、Discord、企微、MQTT、Telegram 等 SDK。不能只因项目定位是“纯网关”就宣称 QQ-only 部署最轻。QQ 模块已读，但未见足以证明通用 QQ 菜单/面板管理闭环的实现。[依赖清单](https://github.com/TencentCloud/octop-gateway/blob/224ed078ce20042fb5fa59240d6e3c7c34bcd67f/pyproject.toml)、[QQ Channel](https://github.com/TencentCloud/octop-gateway/blob/224ed078ce20042fb5fa59240d6e3c7c34bcd67f/src/octop_gateway/channels/qq/channel.py)

### dsh-im：更新参考入口，继续保留

当前包为 5.8.0，使用 `@tencent-connect/qqbot-nodejs` 1.0.4。其 `modern-harness-api.mjs` 直接订阅 Host 的会话/Agent 事件并封装原生操作，是 Companion 边界的主要参考。[包元数据](https://github.com/xmanrui/dsh-im/blob/990ba42fdb06d4768b6d901320519377ce57679a/package.json)、[Host 接口](https://github.com/xmanrui/dsh-im/blob/990ba42fdb06d4768b6d901320519377ce57679a/plugin-src/host/modern-harness-api.mjs)

`qq-menu.mjs` 将菜单绑定操作者和路由，带过期与单次消费；按钮用指令型 action 和 `enter: true`，值得验证其是否满足直接点击执行。其 ADR 还要求出站产物由可信工具显式登记并绑定 Session/Turn，而不是自动扫描助手文本里的本地路径。这是新版任务书值得补充的真实交付边界。[QQ 菜单](https://github.com/xmanrui/dsh-im/blob/990ba42fdb06d4768b6d901320519377ce57679a/src/channels/qq/qq-menu.mjs)、[渠道语义 ADR](https://github.com/xmanrui/dsh-im/blob/990ba42fdb06d4768b6d901320519377ce57679a/docs/adr/0001-semantic-core-native-channel-adapters.md)

### Takopi：可以借鉴任务控制，不能照搬审批

当前源码同时有 exec 和 App Server 路径，默认配置模式为 app_server，包含 `turn/steer`。但 `_handle_server_request()` 对命令/文件审批返回 `accept`，对权限请求返回请求的权限。它与“绝不默认自动批准”冲突，应在参考清单里明确排除这部分行为。[Codex Runner](https://github.com/banteg/takopi/blob/e0123d4f9b2588bf45ec7250ad648c324e20ce20/src/takopi/runners/codex.py)

- **codenoah/codex-telegram-bridge**：原生 app-server 与终端共享路径直观；启动脚本是 Bash，含 nohup、可选 tmux，不能当成 Windows 即装即用方案。[启动脚本](https://github.com/codenoah/codex-telegram-bridge/blob/47a1c80d2a56675a75eea61772eefa3d3e6a6da9/bin/codex-remote)

## QQ 原生交互：已经能确定与仍待验证的部分

`qq-official-bot` 1.3.3 的 `MenuPanelService` 已实际定义菜单及面板 CRUD。源码注释明确：

- `menu.sendMessage()` 和 `panel.command()` 是将文本填入输入框。
- 自定义菜单仅 C2C 生效，更新是覆盖完整配置。
- 面板类型有 command/link，未见声明式参数 schema 或动态候选值接口。
- 消息内 keyboard 与全局菜单、原生指令面板是不同机制。

所以原任务书应保留“无参操作可直接触发”的用户目标，但将实现拆开：原生面板用于命令发现和填入；消息内按钮负责即时执行；枚举参数用分页选择。不能把 SDK 存在 CRUD 方法当成动态补全或自动注册成功。[SDK 实现](https://github.com/zhinjs/qq-official-bot/blob/629a3bc8012dabef1361f97e5823001fbba21b5a/src/services/menu-panel.ts)

以上是 SDK 契约证据，尚未使用真实机器人确认账号权限、QQ 客户端版本和服务端行为。菜单合并必须读取原配置并保留非本网关条目；审批按钮还要绑定原生请求，而不是只携带当前聊天。

## Codex 官方协议更新

根据本次实际打开的 [Codex App Server 官方文档](https://developers.openai.com/codex/app-server)，新版任务书应把以下内容写成按安装版本核验的协议清单：

- `turn/steer` 已有明确方法，需匹配 `expectedTurnId`；历史应使用分页 turns/items 接口。
- 审批和提问是服务端请求；用 `serverRequest/resolved` 撤销旧交互。完整历史一次性返回的旧用法已被弃用。
- 支持 stdio，并有 WebSocket 及 `codex --remote` 共享后端路线；官方仍标注 WebSocket experimental/unsupported。
- 使用本机 CLI 生成版本对应的 TypeScript/JSON Schema，不能靠参考项目中的旧消息结构长期兼容。

这里的共享是“多个客户端连接同一个原生后端”，不自动等于“独立后端可接管任意 Desktop 活跃线程”。HAPI 和微信桥分别展示了共享后端与私有桌面 IPC 两种不同路线。正式选型应继续沿用原文不抢锁、不篡改会话文件的约束。

## 正式实施前的最小验证清单

以下是建议的后续实验，不是本次已完成结果：

1. **现成桥接器淘汰实验**：缺失一个 Agent 二进制/进程时 IM 和另一个 Agent 能否继续；列会话是否产生原生文件写入；能否禁掉不需要的功能。
2. **QQ 交互实验**：同一机器人分别验证面板填入、消息按钮直接触发、回调 ACK、身份归属、旧按钮失效、菜单重复同步不破坏手工项。
3. **Codex 协议实验**：锁定本机版本，用原生接口完成新建、分页历史、Turn、Steer、Interrupt、审批/提问；尝试同后端双客户端，验证桌面持有线程的冲突行为。
4. **DSH 能力实验**：先验证 ACP 的创建、恢复、目录、权限、停止和提问；逐项列出与当前 Desktop Host 的差距，再决定 Companion 范围。
5. **交付恢复实验**：重启或断网后区分“尚未发送”“已接受”“结果未知”；不得自动重发可能已经执行的任务。文件只按明确授权与登记发送。

选择条件：现成桥接器若只需外围配置或独立 Adapter 即可满足硬约束，优先复用；若必须长期改写其会话、权限与生命周期核心，优先采用薄网关。此处是基于本次源码证据的工程判断，尚未完成运行选型。
